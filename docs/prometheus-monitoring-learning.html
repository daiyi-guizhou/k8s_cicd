一、整体链路（数据怎么流动）

理解这套监控只需抓住两件事：

  • Prometheus 是「拉（pull）」模型：它主动去找被监控对象要指标，而不是别人推给它。
  • 所有 Web 入口收口在「网关 + Ingress 的 Host 路由」：无论 Prometheus / Grafana / Alertmanager，浏览器都从同一个网关进来，靠域名（Host 头）区分。

下面这张图是数据/控制平面：被监控对象被 Prometheus 每 15s 拉取 → 写进本地 TSDB 时序库（保留 15 天）→ 同时每 15s 评估规则 → 命中就发告警给 Alertmanager；另一边 Grafana 把 Prometheus 当数据源画出看板。

二、浏览器访问链路

这张图是Web 入口平面：浏览器打 FQDN:9001/:9091 → 本地 nginx 网关（docker 容器，--network host）→ 转发到 K8s Ingress NodePort 30000 → Ingress 按 Host 头路由到对应 Service → Pod。

本地访问前置条件：本机有 HTTP_PROXY=127.0.0.1:9674 会拦截这些 FQDN。所以浏览器访问前要做两件事：① C:\Windows\System32\drivers\etc\hosts 里加上 127.0.0.1 prometheus.monitoring.local 等条目；② 把这些域名（或 *.monitoring.local、*.logging.local）加入代理的 No-Proxy / bypass。否则会看到 502。

三、Pull 网络链路（与网关访问路径的区别）

前面两节分别看了「数据怎么流动」和「人怎么访问页面」。这节把镜头拉到网络包级别：一次 scrape 里，指标到底从哪台机器的内存，走到哪台机器的磁盘。先把结论说清——Pull 模型里，流量由 Prometheus 发起，方向是「Prometheus 出门找后端取」，不是后端推给 Prometheus。

3.1 逐步走一遍（对应本项目真实地址）

  1. 第 0 步 · 服务发现先告诉 Prometheus「连谁」（图上方蓝线）：console-backend job 用 kubernetes_sd_configs，拿 SA token 问 K8s API Server「app=k8s-console-backend 的 Pod 在哪？」K8s 回答 Pod IP（如 10.244.x.x）+ 端口 8000，Prometheus 填进目标的 __address__。这是 pull 能「自动跟随 Pod 漂移」的根本原因。
  2. 第 1 步 · 你的代码把值放进内存：upload_income 执行 user_income.labels(user_id=123, plan="unknown").set(8500)。此时 8500 只活在 backend Pod 里 Django 进程内存中，外部还看不到。
  3. 第 2 步 · Django 把内存暴露成 HTTP 端点：django_prometheus 在 :8000/metrics 挂了处理器，调用 generate_latest() 把进程内所有已注册指标（含 user_income、django_*）序列化成纯文本，等别人来 GET。
  4. 第 3 步 · TCP 连接（Pod → Pod 集群内直连）：Prometheus 抓取循环（每 15s）发起 TCP 10.244.x.x:8000。关键点：这是集群内部 Pod 到 Pod 的流量，走 CNI 网络，不上 NodePort、不经网关、不经 Ingress。
  5. 第 4 步 · HTTP GET /metrics：连上后发 GET /metrics，路径/端口来自 relabel 的 __metrics_path__ 与 __address__（你的 05-backend.yaml 注解 prometheus.io/path: /metrics、port: 8000 在此生效）。
  6. 第 5 步 · 响应：明文指标行回来（图虚线返回箭头）：backend 把第 2 步生成的文本回给 Prometheus，形如 user_income{user_id="123",plan="unknown"} 8500，沿同一个 TCP 连接返回。
  7. 第 6 步 · Prometheus 解析 + 贴标签 + 写盘：每行文本解析成样本（指标名+标签+数值），自动补 job="console-backend"、instance="10.244.x.x:8000" 及 relabel 映射来的 kubernetes_namespace="prd" 等，打上抓取时刻时间戳，写进本地 TSDB（PVC prometheus-data，保留 15 天）。
  8. 第 7 步 · 下游两条支线（图下方琥珀色）：① 告警线——评估循环用 TSDB 跑规则（如 ConsoleBackendDown），命中 POST 给 Alertmanager；② 查询线——Grafana 通过 /api/v1/query 读 Prometheus（也是 HTTP，但方向是「查」）。

3.2 最容易混淆：scrape 根本不走网关

你前面配了 :9001/:9091 网关 + Ingress NodePort 30000——那套只给你（人）的浏览器用，让 prometheus.monitoring.local:9091 能打开页面。而 Prometheus 抓 backend 的链路，完全不经过网关/Ingress/NodePort。对比：

场景路径
你浏览器打开 Prometheus 页面浏览器 → 网关 :9091 → Ingress :30000 → prometheus Service → Pod
Prometheus 抓 backend 指标（scrape）prometheus Pod → 集群网络 → backend Pod IP:8000
推论：「网关挂了」只影响你看图表，不影响监控数据采集；反过来，backend 的 /metrics 因端口/path 不对而 301，人也照样能打开 Prometheus 页面，但 targets 会显示 DOWN。两者解耦，正是 pull 的好处之一。

3.3 为什么这条链路「稳」

  • 目标死了立刻知道：backend Pod 被删 → 下次 GET 失败 → up{job="console-backend"}=0 → 可触发告警（push 模型下这事儿发现不了）。
  • 地址自动跟随：Pod 重启 IP 变了，下次服务发现就拿到新 IP，不用改任何配置。
  • 出站即可：只要 Prometheus 能主动连出去（集群内默认就通），不需要每个后端反向连回中心，防火墙/网络策略更简单。

四、配置详解（都在 deploy/monitoring/02-prometheus.yaml）

Prometheus 的全部行为由它的 ConfigMap（prometheus-config）决定，核心三段：抓取配置 scrape_configs、告警对接 alerting、规则文件位置 rule_files。

3.1 权限：先给 Prometheus 一个「读集群」的身份（RBAC）

K8s 里任何组件想看 nodes/pods/endpoints，都得有 RBAC。文件开头就是：

  • ServiceAccount: prometheus（ns prd）
  • ClusterRole: prometheus：允许 get/list/watch nodes、services、endpoints、pods、configmaps，以及访问非资源 URL /metrics、/metrics/cadvisor
  • ClusterRoleBinding 把它绑到这个 SA
坑：没有这段，下面的 kubernetes_sd_configs（服务发现）就发现不了集群目标。

3.2 抓取配置 scrape_configs：一共 10 个 job

Prometheus 把「去哪抓、怎么抓」拆成一个个 job。按数据源分：

job 名数据源怎么发现目标关键说明
prometheus自己static localhost:9090监控 Prometheus 自身
kubernetes-apiserversAPI Serversd role: endpoints，keep default;kubernetes;httpshttps + 携带 SA 的 token/ca
kubernetes-nodes节点sd role: node节点级指标，labelmap 节点标签
kubernetes-cadvisor容器sd role: node，__metrics_path__=/metrics/cadvisor容器 CPU/内存 的来源
kubernetes-service-endpoints带注解的 Servicesd role: endpoints，keep prometheus.io/scrape=true通用自动发现
kubernetes-pods带注解的 Podsd role: pod，keep prometheus.io/scrape=true同上按 Pod
node-exporternode-exportersd role: endpoints + namespaces: [prd]本次修复的关键点：之前写成 monitoring 导致抓不到，节点面板全空
kube-state-metricskube-state-metricsstatic kube-state-metrics.prd.svc:8080提供 kube_* 对象指标（当前 scaled 0）
console-backend你的 Django 后端sd role: pod + keep app=k8s-console-backend抓 django_*、api_request_latency_* 等业务指标

3.3 两个值得学的概念

① kubernetes_sd_configs（服务发现）：不用手写 IP 列表，Prometheus 直接问 K8s API「现在有哪些 node/pod/endpoint」，自动生成抓取目标。集群扩缩容它自己跟着变。

② relabel_configs（重打标签）：发现出来的目标带一堆内部标签（__meta_kubernetes_*），用 relabel 来「保留 / 改写 / 贴标签」。比如 kubernetes-service-endpoints 里：

  • keep ... prometheus.io/scrape: true → 只抓显式声明要监控的 Service；
  • replace ... prometheus.io/port → 把注解里的端口拼进 __address__；
  • labelmap __meta_kubernetes_service_label_(.+) → 把 K8s 的 service 标签变成 Prometheus 的标签。
这套机制是 K8s 监控「零配置自动发现」的核心。想加一个新要监控的服务，只要给它打上 prometheus.io/scrape: "true" 等注解即可，不用改 Prometheus 配置。

3.4 存储与部署（文件后半段）

  • 镜像 prom/prometheus:v2.53.3，启动参数：--storage.tsdb.path=/prometheus、--storage.tsdb.retention.time=15d（数据保留 15 天）、--web.enable-lifecycle（支持热加载 /-/reload）。
  • 持久化：PVC prometheus-data 10Gi，accessModes: ReadWriteOnce（RWO，单节点够用）。
  • 一个坑（已修）：strategy: Recreate。默认 RollingUpdate 滚动更新时会起一个新 Pod，新旧 Pod 同时挂同一个 RWO PVC → opening storage failed: lock DB directory 崩溃循环。单副本 + RWO 必须用 Recreate，先删旧的再起新的。

3.5 告警对接

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager.prd.svc:9093"]

Prometheus 自己只负责「判断要不要告警」，真正「发给谁、怎么发」交给 Alertmanager。规则文件位置由 rule_files: ["/etc/prometheus/rules/*.yml"] 指定（挂的第二个 ConfigMap prometheus-rules）。

五、规则详解（11 条，3 个组，在 prometheus-rules ConfigMap）

规则文件结构 = groups → 每个 group 有 rules → 每条 rule 是 alert + expr + for + labels + annotations。

组 1：kubernetes-apps（4 条，看业务容器）

告警表达式核心含义
HighPodCPUsum(rate(container_cpu_usage_seconds_total[5m])) by (pod,ns) > 0.8单 Pod CPU > 0.8 核
HighPodMemorycontainer_memory_working_set_bytes / kube_pod_container_resource_limits > 0.8内存占用超 limit 80%
PodCrashLoopingincrease(kube_pod_container_status_restarts_total[15m]) > 315 分钟内重启 >3 次
PodNotReadysum(kube_pod_status_ready{condition="true"}) == 0Pod 长时间 NotReady

组 2：kubernetes-nodes（2 条，看节点）

告警表达式核心含义
HighNodeCPU100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))*100 > 90节点 CPU > 90%
HighNodeMemory(1 - MemAvailable/MemTotal)*100 > 90节点内存 > 90%

组 3：console-app（5 条，看你的后端）

告警表达式核心含义
ConsoleBackendDownup{job="console-backend"} == 0后端挂了
HighErrorRaterate(django_http_responses_total_by_status_total{status=~"5.."}[5m]) > 0.15xx 错误率
DatabaseConnectionHighdjango_db_connections_total > 80数据库连接数
HighLogErrorRaterate(django_log_errors_total[5m]) > 2错误日志速率
SlowAPIResponseshistogram_quantile(0.95, rate(api_request_latency_seconds_bucket[5m])) > 2API P95 延迟 > 2s

4.1 告警生命周期（值得记）

  1. expr 每 15s 算一次；
  2. 结果为真且持续超过 for: 5m（避免抖动误报）→ 状态变 PENDING→FIRING；
  3. FIRING 的告警推给 Alertmanager；
  4. Alertmanager 按 route 分组（group_by: [alertname, severity]）、去重、按 repeat_interval 重复，再交给 receiver。
当前实测：11 条规则全部加载，0 firing（集群健康）。

4.2 Alertmanager 配置（06-alertmanager-config.yaml）

route:
  receiver: "null"        # 默认接收器
  routes:
    - match: {severity: critical}
      receiver: "null"    # critical 也走 null
receivers:
  - name: "null"          # 空接收器：只记录，不往外发
现状：所以现在告警能触发、能在 Prometheus/Alertmanager 页面看到，但不会发邮件 / 钉钉 / Webhook。想真通知，把 null 换成 webhook_configs / email_configs 等，再 kubectl rollout restart deployment/alertmanager -n prd。详见 docs/监控使用指南.md §4.4。

六、当前状态的两个未决项

① kube-state-metrics 是 scaled 0（镜像代理拉不到）。所以依赖 kube_* 的 3 条规则（PodCrashLooping / PodNotReady / HighPodMemory 分母）目前 No Data；Grafana 那两个面板已改成 cadvisor 等价查询兜底，所以看板照样有数。镜像可达后 kubectl rollout restart deployment/kube-state-metrics -n prd 即可补全。
② Alertmanager receiver: null：如上，告警不外出。这是「能看但不能通知」，需要接真实通知渠道才完整。

七、学习重点（划重点）

  • pull 模型 + 服务发现：Prometheus 主动抓，靠 kubernetes_sd_configs 自动找目标，靠 relabel_configs 过滤 / 贴标签。
  • TSDB 是时序数据库：每个指标 = 名字 + 一组标签 + 时间戳样本；查的时候用 PromQL 按标签筛。
  • 规则分 alerting（告警）和 recording（预计算）两类，本项目只用 alerting。
  • for 子句防抖；Alertmanager 负责分组 / 静默 / 路由 / 通知，和 Prometheus 解耦。
  • 入口收口：所有 Web 访问都过网关(9001/9091) + Ingress Host 路由，本地还要配 hosts 和代理 bypass。
