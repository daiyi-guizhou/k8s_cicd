一、数据链路全景

当前项目日志从生成到可查询的完整路径：

Django logger.info() │ ├── StreamHandler("console") ──▶ sys.stderr (fd 2) ├── StreamHandler("json_console") ──▶ sys.stderr (fd 2) └── RotatingFileHandler("file") ──▶ /app/logs/api.log (容器内, Fluentd 看不到) │ ┌─────────┘ │ (fd 2) ▼ containerd ──接管容器的 stdout/stderr──▶ CRI 格式化: "2026-07-21T14:18:15Z stdout F {json}" │ ▼ /var/log/containers/k8s-console-backend-*.log (宿主机 = WSL2 Linux VM) │ ▼ Fluentd DaemonSet ──hostPath:/var/log──▶ tail CRI 文件 │ regexp 解析 CRI 壳 │ kubernetes_metadata 加 pod 名 ▼ Elasticsearch ──索引 k8s-YYYY.MM.DD │ ▼ Kibana ──查询、过滤、时间轴
关键发现： RotatingFileHandler("/app/logs/api.log") 写的日志 Fluentd 采集不到！ 只有 StreamHandler（stdout/stderr）才被 containerd 捕获。

二、StreamHandler vs RotatingFileHandler

问题

把 RotatingFileHandler 的 filename 改成 /dev/stdout，能被 containerd 接管吗？rotation 能正常工作吗？

实验结果（在 backend 容器中实测）

# 5 条日志，每条都爆了 error
--- Logging error ---
  File "/usr/local/lib/python3.12/logging/handlers.py", line 73, in emit
    if self.shouldRollover(record):
  File "/usr/local/lib/python3.12/logging/handlers.py", line 193, in shouldRollover
    pos = self.stream.tell()
io.UnsupportedOperation: underlying stream is not seekable

# 但 doRollover() 显示 SUCCESS
ROTATION SUCCESS

结论

Handlercontainerd 可见自动 rotation原因
StreamHandler() YES 不涉及 写 fd 1/2，containerd 直接捕获
RotatingFileHandler('/dev/stdout') YES NO shouldRollover() 调 tell()，管道不可 seek
RotatingFileHandler('/app/logs/api.log') NO YES 写到容器本地文件，containerd 不监控此 fd
核心矛盾：要 containerd 捕获 → 必须写 stdout（管道），但管道不支持 tell()，rotation 机制失效。 要 rotation 正常工作 → 必须写普通文件，但普通文件 containerd 看不到。 鱼和熊掌不可兼得。

三、/dev/stdout 与管道不可 seek 的本质

文件 vs 管道

普通文件 (regular file)管道 (pipe)
比喻一本书一条河
数据存储磁盘上持久存储内存缓冲区，流过去就消失
文件指针有位置（"第几页"）没有位置概念
tell()✅ "书签夹在第几页"❌ 无法回答"水流到第几米了"
seek(0)✅ 翻回第一页❌ 水过去了回不来
访问模式随机访问顺序流

RotatingFileHandler.shouldRollover() 的调用链

emit(record)
  → shouldRollover(record)   // 第1步：判断要不要旋转
      → self.stream.tell()   // ← 炸了！io.UnsupportedOperation
  → doRollover()             // 第2步：做旋转（永远到不了这里）
  → FileHandler.emit()       // 第3步：真正写日志

为什么 doRollover() 显示 SUCCESS？

doRollover() 操作的是 /dev/stdout（路牌），不是 pipe（河）：

  1. os.rename('/dev/stdout', '/dev/stdout.1') — 把路牌搬走
  2. devtmpfs 自动补位 — 新路牌瞬间生成
  3. open('/dev/stdout', 'a') — 打开新路牌

路牌在原地，河还在流。SUCCESS 是假的，什么都没变。

四、symlink：名字与位置的解耦

symlink 是什么？

符号链接是一个特殊文件，存的内容不是数据，而是一条路径。访问时 OS 自动追到目标。

# 创建
$ ln -s /real/file.txt shortcut.txt
$ cat shortcut.txt  # OS 自动追到 /real/file.txt

# 对比
hard link: 两个名字 → 同一个 inode (同一本书有两个封面)
symlink:   存一个路径 → 另一个 inode   ("封面写的是另一本书的位置")

解决什么问题？

场景示例效果
版本切换 /usr/bin/python → python3.12 所有脚本写 #!/usr/bin/python，升级只改一个链接
目录重定向 /var/log → /data/ssd/log 日志写 /var/log，实际落到 SSD，应用代码不动
设备抽象 /dev/stdout → /proc/self/fd/1 任何程序硬编码 /dev/stdout，不问 stdout 实际连什么

/dev/stdout → /proc/self/fd/1 的精妙之处

/proc/self 是一个魔法的东西——谁读它，它就变成谁的 PID：

Process A (PID=100) 读 /proc/self/fd/1 → /proc/100/fd/1 → A 的 stdout Process B (PID=200) 读 /proc/self/fd/1 → /proc/200/fd/1 → B 的 stdout

这意味着 /dev/stdout 是 "当前进程的标准输出，不管它是什么"：

  • 终端 → /dev/stdout 就是终端
  • 管道（containerd 捕获）→ /dev/stdout 就是那条管道
  • 重定向到文件 → /dev/stdout 就是那个文件

五、四种日志采集方案对比

假设 backend 有 4 个 Pod，需要把 /app/logs/api.log（RotatingFileHandler 写的）也采集到 ES：

方案复杂度可靠性格式统一K8s 原生
A. 纯 stdout（删 RotatingFileHandler） 极低 ✅ containerd 兜底 ✅ 单管道 CRI ✅ 12-factor
B. Sidecar 容器 中 ⚠️ sidecar 多一个故障点 ❌ CRI + 裸日志两套 ✅
C. PV/PVC + hostPath 高 ⚠️ 多副本写冲突 ❌ 两套格式 ⚠️ 重
D. 网络直推 (SocketHandler) 中 ❌ 网络断了就丢 ✅ JSON 直传 ❌ 反模式
当前项目已有 console + json_console 走 stdout，Fluentd 已在采 CRI 日志。 方案 A 是最自然的选择——删掉 file handler，日志留存交给 ES index lifecycle management。

六、sidecar 模式、emptyDir 与 fluent-bit

sidecar 是什么？

不是技术，是部署模式。主容器做业务，sidecar 做辅助（日志、代理、配置热加载）。同一个 Pod，共享网络和 volume，共享生命周期。

┌─────────────────────────┐ │ Pod │ │ ┌─────────────────┐ │ │ │ backend (Django) │ │ 写日志到 /shared/logs │ └────────┬────────┘ │ │ │ emptyDir │ │ ┌───────▼────────┐ │ │ │ fluent-bit │────│──▶ ES │ │ tail /shared/log│ │ 读日志并转发 │ └────────────────┘ │ └─────────────────────────┘

emptyDir 是什么？

K8s 临时卷。Pod 创建时在 Node 上划一块空间，Pod 内所有容器共享读写。Pod 删除即消失。不需要提前建 PV/PVC，零配置。

volumes:
  - name: log-share
    emptyDir: {}           # 就这一行

fluent-bit 如何推 ES？

fluent/fluent-bit:3.1 是一个单个 C 二进制文件（~10MB），Input/Filter/Output 全部编译在内。ES Output 插件底层调的是 Elasticsearch 的 POST /_bulk HTTP API：

# fluent-bit sidecar 内部逻辑
# 1. tail 读到一行 JSON 日志
# 2. 放内存 buffer，攒够 500 条或 5 秒
# 3. 拼成 ES Bulk 格式发送

POST http://elasticsearch.prd.svc:9200/_bulk
Content-Type: application/x-ndjson

{"index":{"_index":"app-file-logs-2026.07.21"}}
{"time":"2026-07-21T14:30:00Z","level":"INFO","msg":"GET /api 200"}
{"index":{"_index":"app-file-logs-2026.07.21"}}
{"time":"2026-07-21T14:30:01Z","level":"ERROR","msg":"timeout"}

七、SocketHandler、Kafka 与网络直推

SocketHandler 是什么？

TCP 长连接，裸数据流。非 HTTP。Python 端打开 TCP 连接到 Fluentd，每条日志发一个 JSON 行。

HTTP POSTSocketHandler
连接每次发完就断长连接
格式HTTP headers + body纯数据，无头
开销高低
可靠应用层确认只管发

可以用 Kafka 吗？

可以，这是大厂标配。但当前项目 10 个 Pod，加了属于过度设计。

Django ──▶ Kafka Topic ──▶ Fluentd Consumer ──▶ ES │ └── 持久化缓冲：ES 挂了也不丢 峰值流量削峰填谷 多个消费者可复用同一份日志
不加 Kafka加 Kafka
Fluentd/ES 挂了 → 日志丢Kafka 存着 → 恢复后继续消费
峰值条数/秒 → ES 扛不住Kafka 缓存 → 平滑消费
0 运维成本多一套 Kafka 集群

八、多 Pod 日志时序问题 — 三件套

问题

4 个 backend Pod 同时写日志，如何保证 ES 里按真实时间排序不混乱？

真相：当前 @timestamp 是谁的时间？

CRI 日志行: 2026-07-21T14:51:23.154197023Z stderr F {"time": "...", "level": "INFO", ...} └────── CRI 时间 ──────┘ └── 这才是 app 真实时间 Fluentd regexp: expression /^(?<time>.+?)\s+(?<stream>stdout|stderr)\s+[FP]\s+(?<log>.*)$/ ↑ 取了 CRI 的时间！ 结果: ES @timestamp = containerd 读管道的时间，不是 app 调 logger.info() 的时间

解法三件套

件作用当前状态
时钟同步 4 个 Pod 的时间基准一致 ✅ 同 Node 共享内核时钟
源头时间戳 @timestamp 用 app 的 "time" 字段而非 CRI ❌ 需修
Pod 身份 每条日志带 pod name ✅ kubernetes_metadata 已加

Fluentd 配置修复

<!-- 现在：废的（拿 JSON 去匹配 CRI 正则） -->
<filter kubernetes...**k8s-console-backend**.log>
  <parse>
    @type regexp          <!-- 匹配不上，被 emit_invalid false 吞掉 -->
    ...

<!-- 改成：解析 JSON，用 app 的 "time" 覆盖事件时间 -->
<filter kubernetes.var.log.containers.**k8s-console-backend**.log>
  @type parser
  key_name log
  reserve_data true        <!-- 保留原始字段 -->
  <parse>
    @type json
    time_key time           <!-- JSON 里的 "time" 字段 -->
    time_format %Y-%m-%d %H:%M:%S
  </parse>
</filter>

九、Request ID：跨 Pod 请求追踪

为什么需要？

一个请求可能跨 Pod：Pod-A 处理 HTTP → 调 Pod-B 的 gRPC。需要把两条日志串在一起。

GET /api/orders/123 │ X-Request-ID: req-abc-123 │ ├── Pod-A: {"time":"14:51:23","request_id":"req-abc-123","msg":"收到请求"} │ │ HTTP 调 Pod-B, 透传 header │ └── Pod-B: {"time":"14:51:24","request_id":"req-abc-123","msg":"查数据库"} │ ▼ Kibana: filter request_id:"req-abc-123" → 全出来了

Django 三步实现

# 1. Middleware — 生成/读取 ID
class RequestIDMiddleware:
    def __call__(self, request):
        request.request_id = request.headers.get(
            "X-Request-ID", str(uuid.uuid4()))
        _local.request_id = request.request_id   // 存到线程本地
        response = self.get_response(request)
        response["X-Request-ID"] = request.request_id
        return response

# 2. Filter — 注入到每条日志
class RequestIDFilter(logging.Filter):
    def filter(self, record):
        record.request_id = getattr(_local, "request_id", "-")
        return True

# 3. Formatter — 输出到 JSON
"json": {
    "format": '"time":"%(asctime)s","request_id":"%(request_id)s",...'
}
