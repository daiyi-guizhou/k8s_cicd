## 二、在浏览器里看监控（两种访问方式）

### 方式一：`kubectl port-forward`（✅ 强烈推荐，最简单可靠）

本机开了 HTTP 代理（如 `HTTP_PROXY=127.0.0.1:9674`），会拦截 `*.monitoring.local` / `*.logging.local` 这类域名；而 **`localhost` 在代理的 NO_PROXY 白名单里**，所以用端口转发到 `localhost` 能 100% 绕过代理，不需要改 hosts、不需要配代理 bypass。

开三个终端（或用 `&` 后台），分别转发：

```bash
# 1) Prometheus（指标查询 / 告警规则）
kubectl port-forward -n prd svc/prometheus 9090:9090
# 浏览器打开：http://localhost:9090

# 2) Grafana（图形化看板）
kubectl port-forward -n prd svc/grafana 3000:3000
# 浏览器打开：http://localhost:3000   （账号 admin / 密码 admin）

# 3) Alertmanager（告警分发状态）
kubectl port-forward -n prd svc/alertmanager 9093:9093
# 浏览器打开：http://localhost:9093
```

> 端口转发只在终端开着时有效，关掉终端就断开。重新开浏览器前先确认转发还在跑。

### 方式二：本地网关 + 域名（推荐长期使用）

网关 `k8s-gateway` 同时监听 **:9001** 和 **:9091**，按 `Host` 头转发到 K8s Ingress。已配置：
- `:9001` → Grafana、Kibana、Console 前端
- `:9091` → **Prometheus**、**Alertmanager**（本次新增）

**① 补 hosts 条目**（管理员权限编辑 `C:\Windows\System32\drivers\etc\hosts`）。
已存在：`k8s-cicd.daiyi.local.com`、`grafana.monitoring.local`、`kibana.logging.local`。
还需确保有（本次已自动追加，若重装系统请补上）：

```
127.0.0.1 prometheus.monitoring.local
127.0.0.1 alertmanager.monitoring.local
```

> `alertmanager` 现已建 Ingress（`deploy/monitoring/09-alertmanager-ingress.yaml`），可经网关 `:9091` 访问。

**② 把监控/日志域名加入代理 bypass**（否则浏览器会把请求甩给本机代理 → 502）。
把下面这些加进系统/浏览器的「不使用代理」列表：

```
grafana.monitoring.local;prometheus.monitoring.local;alertmanager.monitoring.local;kibana.logging.local;*.monitoring.local;*.logging.local
```

配置好后用这些地址访问：

```
http://grafana.monitoring.local:9001/          # Grafana（:9001）
http://kibana.logging.local:9001/              # Kibana（:9001，日志）
http://prometheus.monitoring.local:9091/       # Prometheus（:9091）
http://alertmanager.monitoring.local:9091/     # Alertmanager（:9091）
```

> 💡 资源管理页 `http://k8s-cicd.daiyi.local.com:9001/` 顶部已内置「🔗 监控与日志」快捷入口，一键跳转以上四个地址。

## 三、怎么看指标和看板

### 3.1 Prometheus —— 查原始指标 / 写查询

打开 `http://localhost:9090`：

1. 顶部 **Graph** 页 → 输入 PromQL → **Execute**。
2. **Status → Targets** 看所有抓取目标是否 `up`。
3. **Status → Rules** 看已加载的告警规则与是否触发。
4. **Alerts** 页看当前 firing 的告警（绿=正常，红=firing）。

### 3.1.1 真实告警规则对应的 PromQL（可直接粘贴到 Graph 执行）

下面每一条都来自 `deploy/monitoring/02-prometheus.yaml` 里 `prometheus-rules` 的**真实 `expr`**；保留原样就是该告警的触发条件，去掉末尾的 `> 阈值` 就是可查趋势的曲线。

| 规则组 | 告警名 | 真实查询 / 触发表达式 |
|--------|--------|----------------------|
| kubernetes-nodes | HighNodeCPU | `100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90` |
| kubernetes-nodes | HighNodeMemory | `(1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100 > 90` |
| kubernetes-apps | HighPodCPU | `sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (pod, namespace) > 0.8` |
| kubernetes-apps | HighPodMemory | `sum(container_memory_working_set_bytes{container!="",pod!=""}) by (pod, namespace) / sum(kube_pod_container_resource_limits{resource="memory"}) by (pod, namespace) > 0.8` |
| kubernetes-apps | PodCrashLooping | `increase(kube_pod_container_status_restarts_total[15m]) > 3` |
| kubernetes-apps | PodNotReady | `sum(kube_pod_status_ready{condition="true"}) by (pod, namespace) == 0` |
| console-app | ConsoleBackendDown | `up{job="console-backend"} == 0` |
| console-app | HighErrorRate | `rate(django_http_responses_total_by_status_total{status=~"5.."}[5m]) > 0.1` |
| console-app | DatabaseConnectionHigh | `django_db_connections_total > 80` |
| console-app | HighLogErrorRate | `rate(django_log_errors_total[5m]) > 2` |
| console-app | SlowAPIResponses | `histogram_quantile(0.95, rate(api_request_latency_seconds_bucket[5m])) > 2` |

想看"当前值/趋势"而不看是否触发，把末尾的 `> 阈值` 去掉即可，例如：

```promql
# HighNodeCPU 的实时曲线（去掉 >90）
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# HighPodMemory 的实时值
sum(container_memory_working_set_bytes{container!="",pod!=""}) by (pod, namespace) / sum(kube_pod_container_resource_limits{resource="memory"}) by (pod, namespace)

# PodCrashLooping 的当前值（近 15 分钟重启次数）
increase(kube_pod_container_status_restarts_total[15m])
```

> `django_*`、`api_request_latency_*` 来自 Console Backend（Pod 注解开了 `prometheus.io/scrape`）；`kube_*` 来自 **kube-state-metrics**（本次新增，见 §六 `08-kube-state-metrics.yaml`）。若这些指标查不到，先到 Prometheus **Status → Targets** 确认对应 job 是否 `up`。

### 3.2 Grafana —— 图形化看板（推荐日常看）

打开 `http://localhost:3000`，登录 `admin / admin`。

- **数据源**：已自动预置 `Prometheus`（`http://prometheus.prd.svc:9090`），开箱即用。
- **预置看板**：`K8s Cluster Overview`（路径：左侧 ☰ → Dashboards），含 4 个面板：
  - Node CPU Usage、Node Memory Usage（来自 node-exporter，已修复抓取命名空间）
  - Pod 数 by Namespace、Top 内存 Pod（来自 cadvisor，无需额外组件即可出数）
  > 注：原看板的 `Pod Count by Namespace` / `Deployment Replicas` 依赖 `kube-state-metrics` 的 `kube_*` 指标；因环境镜像代理暂不可达该组件镜像，已改为基于 cadvisor 的等价查询，保证看板始终有数据。若后续部署了 kube-state-metrics，可改回 `kube_*` 查询。
- **自建面板**：进某个 Dashboard → **Add panel** → 选数据源 Prometheus → 粘贴上面的 PromQL → 保存。
- **导入社区看板**：☰ → Connections → Data sources 确认 Prometheus 在线后，可去 <https://grafana.com/grafana/dashboards/> 导入经典模板（如 Node Exporter Full `1860`、Kubernetes Cluster Monitoring）。

## 四、如何打开 Prometheus 设置告警

告警链路：**Prometheus 评估规则 → 触发(firing) → 推给 Alertmanager → 按 route 分发给 receiver（邮件/Webhook/Slack 等）**。

### 4.1 现状：规则已存在，但"不通知"

- Prometheus 已加载 **11 条规则**（3 组）：
  - `console-app`（5 条）：`ConsoleBackendDown`、`HighErrorRate`、`DatabaseConnectionHigh`、`HighLogErrorRate`、`SlowAPIResponses`
  - `kubernetes-apps`（4 条）：`HighPodCPU`、`HighPodMemory`、`PodCrashLooping`、`PodNotReady`
  - `kubernetes-nodes`（2 条）：`HighNodeCPU`、`HighNodeMemory`
- 但 Alertmanager 当前 `receiver: "null"` —— **规则会触发，却只记录、不推送任何通知**。这是当前最大短板。

### 4.2 查看已有告警

- Prometheus UI → **Alerts** 页：绿=未触发，红=firing。
- Alertmanager UI（`http://localhost:9093`）→ **Alerts** 页：看收到的告警与分发状态。

### 4.3 新增 / 修改告警规则

规则写在 `deploy/monitoring/02-prometheus.yaml` 里的 **`prometheus-rules` ConfigMap**（`alerts.yml`）：

```yaml
# deploy/monitoring/02-prometheus.yaml 节选
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-rules
  namespace: prd
data:
  alerts.yml: |
    groups:
      - name: console-app
        rules:
          - alert: ConsoleBackendDown      # ← 告警名
            expr: up{job="console-backend"} == 0   # ← 触发表达式
            for: 2m                        # ← 持续 2 分钟才告警
            labels:
              severity: critical           # ← 严重级别
            annotations:
              summary: "Console backend pod is down"
```

**改完生效步骤**（ConfigMap 变更不会自动热加载）：

```bash
# 1) 应用新规则
kubectl apply -f deploy/monitoring/02-prometheus.yaml

# 2) 重启 Prometheus 加载（或用热加载，见下）
kubectl rollout restart deployment/prometheus -n prd

# 可选：不重启，直接热加载（需先 port-forward 9090）
# curl -X POST http://localhost:9090/-/reload
```

### 4.4 让告警真正"通知"出来（接真实渠道）

当前 `deploy/monitoring/06-alertmanager-config.yaml` 的接收器是 `null`。下面以 **Webhook** 为例（企业微信/钉钉/飞书机器人本质都是 Webhook）：

```yaml
# deploy/monitoring/06-alertmanager-config.yaml
data:
  alertmanager.yml: |
    global:
      resolve_timeout: 5m
    route:
      group_by: ["alertname", "severity"]
      group_wait: 10s
      group_interval: 10s
      repeat_interval: 1h
      receiver: "default-webhook"        # ← 改成你的接收器
      routes:
        - match:
            severity: critical
          receiver: "default-webhook"
          repeat_interval: 30m
    receivers:
      - name: "default-webhook"
        webhook_configs:
          - url: "https://your-bot.example.com/webhook"   # ← 换成你的机器人地址
            send_resolved: true
    # 也可以用 email_configs / slack_configs / wechat_configs 等
```

**生效步骤**：

```bash
kubectl apply -f deploy/monitoring/06-alertmanager-config.yaml
kubectl rollout restart deployment/alertmanager -n prd
```

> 改完后去 Alertmanager UI（`http://localhost:9093` → Status）确认 `config receivers` 里出现了你配的接收器。

### 4.5 告警规则 / 通知的自测

1. 故意让某 Pod 异常或把阈值调很低 → 等 `for` 时长 → Prometheus **Alerts** 变红。
2. 到 Alertmanager **Alerts** 看是否收到，并按 route 分发给你的 Webhook（看机器人有没有消息）。
3. 恢复正常 → Alertmanager 显示 `RESOLVED` 并（若 `send_resolved: true`）推送恢复通知。

## 五、常见问题排查（FAQ）

| 现象 | 原因 | 解决 |
|------|------|------|
| 浏览器开 `*.monitoring.local` / `*.logging.local` 报 502 / 空白 | 本机 HTTP 代理拦截了这些 FQDN | 把域名加入代理 bypass（见 §二 ②）；或用 `localhost` 的 port-forward |
| Prometheus / Alertmanager 经 `:9091` 打不开 | hosts 缺条目，或代理拦截 FQDN | 补 hosts（`prometheus/alertmanager.monitoring.local` → 127.0.0.1）+ 加代理 bypass |
| Grafana 看板面板无数据 | ① node-exporter 抓取命名空间曾配错（`monitoring` 应为 `prd`），节点面板空；② 原 `Pod 数`/`Deployment 副本` 面板依赖 `kube-state-metrics` 的 `kube_*` 指标，而该组件镜像当前被镜像代理拦截拉不到 | **已修复**：node-exporter 命名空间改 `prd`（节点面板恢复）；看板另两个面板改为基于 cadvisor 的等价查询，4 个面板现已全部出数。`kube-state-metrics` 镜像可达后 `kubectl rollout restart deployment/kube-state-metrics -n prd` 即可启用 `kube_*` 指标与对应告警规则 |
| 改了告警规则不生效 | ConfigMap 变了，Prometheus 不会自动重载 | `kubectl rollout restart deployment/prometheus -n prd`（或 `/-/reload`） |
| 改了告警规则不生效 | ConfigMap 变了，Prometheus 不会自动重载 | `kubectl rollout restart deployment/prometheus -n prd`（或 `/-/reload`） |
| 告警触发了但没人收到通知 | Alertmanager 接收器是 `null` | 按 §4.4 配真实 receiver 并 rollout restart alertmanager |
| Grafana 登录失败 | 默认 `admin/admin` | 用 `admin/admin`；若被改过，查 `deploy/monitoring/04-grafana.yaml` 的 `GF_SECURITY_ADMIN_*` |
| Prometheus Targets 有 1 个 DOWN | 某带 `prometheus.io/scrape` 注解的 Service 无就绪后端 Pod | 不影响整体；检查该 Service 的后端即可 |
| port-forward 终端一关就断 | 转发是前台进程，关终端即退出 | 让它一直开着；或加 `&` 后台运行 |
