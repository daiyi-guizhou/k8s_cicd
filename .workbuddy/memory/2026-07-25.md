## 部署后访问 http://k8s-cicd.daiyi.local.com:9001/ 报 502 的排查与修复

### 现象
- 浏览器访问 FQDN:9001 返回 502 Bad Gateway（响应头带 `Proxy-Connection`，是代理回的）。
- 直连集群 ingress NodePort 30000（`curl localhost:30000 -H 'Host: k8s-cicd.daiyi.local.com'`）返回 200，页面正常 → K8s 侧完全健康。
- 网关容器 `k8s-gateway` 状态 `Exited (1)` → 9001 没监听。

### 根因 1（网关崩溃，已修）
nginx 网关容器启动时报 `host not found in upstream "host.docker.internal"` → 容器 emerg 退出。
Docker Desktop 某些环境下容器默认 DNS 解析不到 `host.docker.internal`。
修复：`deploy/gateway/start.sh` 的 `docker run` 增加 `--add-host=host.docker.internal:host-gateway`。

### 根因 2（浏览器侧代理拦截，需用户侧处理）
环境存在本地代理 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:9674/`，
`NO_PROXY=localhost,127.0.0.1,::1` **不含** `k8s-cicd.daiyi.local.com`。
→ 浏览器用 FQDN 访问时被甩给代理，代理拉不到本地域名 → 502。
修复（网关配置增强）：在 `deploy/gateway/nginx.conf` 增加 map，把 `localhost/127.0.0.1` 的 upstream Host 重写为 `k8s-cicd.daiyi.local.com`，
使 `http://127.0.0.1:9001/` 可直接访问（127.0.0.1 在 NO_PROXY，绕过代理）。
FQDN 要正常用，需把 `k8s-cicd.daiyi.local.com` 及 `*.local.com` 加入该代理的 bypass/No-Proxy 列表。

### 验证结果
- `http://127.0.0.1:9001/` → 200（页面 "K8s Management Console"），`/api/health` → 200。
- `http://k8s-cicd.daiyi.local.com:9001/ --noproxy` → 200。
- 集群侧：ingress-nginx 1/1 Running，NodePort 80:30000；backend(2/2)/frontend(1/1) 就绪；ELK 与监控全部就绪。

### 备注
本次网关是手动 start.sh 拉起的（此前 deploy-all.sh --skip-build 的 Step 7/8 未确认跑完，
但集群状态已健康）。后续若重跑部署，start.sh 已含 --add-host 修复。

## backend 日志搜集链路排查与修复（同一天后续）

### 链路架构
Django 写 JSON 日志 → 共享卷 /shared/logs/*.json.log → filebeat 边车 tail → Kafka topic `logs.k8s-console-backend` → fluentd 消费 → Elasticsearch(index `k8s-YYYY.MM.DD`, logstash_prefix=k8s) → Kibana 查看。

### 发现的故障（链路原不通）
1. filebeat 报 `Dropping event: no topic could be selected`：原配置 `topic: "logs.%{[service]}"` 依赖 JSON 里的 `service` 字段；但 /shared/logs 里有大量非 JSON 行（Prometheus `/metrics` 响应体 `python_info{...}`、`#` 注释被中间件写进了同一文件），这些行 json 解析失败 → `service` 取不到 → topic 变空被丢弃。
2. fluentd 早前报 `Kafka::UnknownTopicOrPartition`：topic 从未被创建（因 filebeat 一直丢弃）。
3. fluentd 早前 `no address for elasticsearch.prd.svc` 是崩溃循环时的旧日志；实测 `getent` 现在能解析 ES（DNS 正常）。

### 修复
- `deploy/logging/07-filebeat-config.yaml`：把 `output.kafka.topic` 硬编码为 `logs.k8s-console-backend`、`key: k8s-console-backend`（该 ConfigMap 仅挂载在 backend pod，硬编码安全）。`kubectl apply` + `rollout restart deployment/k8s-console-backend`。
- Kafka topic `logs.k8s-console-backend` 已存在（AUTO_CREATE 开启后自动建出）。

## backend 日志清洗：JsonFormatter 根因修复（用户要求"顺手修，不记录 /metrics 响应体"）

### 真正的根因（比 /metrics 更普遍）
`backend/k8s_console/settings.py` 的 `LOGGING.formatters.json` 不是真 JSON 序列化，而是用
`%()` 字符串模板手工拼：`'{"message":"%(message)s",...}'`，**不对 message 做任何转义**。
只要日志 message 含双引号（如 `resp={"status": "ok"}`）或换行（Prometheus /metrics 文本），
拼出的 JSON 就破损 → filebeat 报 `Error decoding JSON`。这才是 filebeat 持续报错的真正来源，
之前统计到 2346 条裸 `# HELP`/`python_info` 续行也是它造成的。/metrics 只是触发因子之一。

### 修复（3 处，已重建镜像并 rollout restart backend）
1. `backend/k8s_console/middleware.py` `ApiLoggingMiddleware.__call__`：对 `request.path` 以 `/metrics` 结尾的请求直接 `return self.get_response(request)`，跳过整条 api 日志（避免高频 scrape 刷屏 + 不写 Prometheus 文本）。
2. `backend/k8s_console/logging_filters.py`：新增 `class JsonFormatter(logging.Formatter)`，用 `json.dumps({...}, ensure_ascii=False)` 严格序列化每条记录（对 message/字段正确转义）。
3. `backend/k8s_console/settings.py` `LOGGING.formatters.json`：改为 `"()": "k8s_console.logging_filters.JsonFormatter"` + `datefmt`，弃用破模板。

### 验证（新 Pod k8s-console-backend-6c78dd69c8-kqmmr）
- 触发 /metrics×2 与 /api/health×2：`/metrics` 日志行 = 0；全部 4 行日志 `json.loads` 成功（invalid 0，含响应体带引号的行）。
- `kubectl logs ... -c filebeat | grep -c "Error decoding JSON"` = 0。
- 日志链路：每行合法 JSON → filebeat 正常 publish → Kafka → fluentd → ES → Kibana。

- 历史 ES 索引 `k8s-2026.07.25` 里可能有少量早期畸形文档（filebeat 降级发布的带 error 字段记录）；新数据完全干净。如需彻底干净可在 Kibana 重建/rollover 索引（会丢历史日志，按需）。

## deploy-all.sh / clean-all.sh 拆分为组件脚本（用户要求"太大了，帮我拆分下"）

### 拆分结构（共 12 个脚本，全部 `bash -n` 通过）
原 `deploy-all.sh`、`clean-all.sh` 是 800+ 行的胖脚本，已重构为「调度器 + 5 个组件脚本」。

**调度器（2 个）**
- `deploy/deploy-all.sh`：解析组件名 + 标志位，循环调用 `deploy/deploy-<comp>.sh`。
- `deploy/clean-all.sh`：解析组件名 + 标志位，循环调用 `deploy/clean-<comp>.sh`。

**组件脚本（5 套，每套含 deploy + clean）**
1. `ingress-controller` → `deploy-ingress-controller.sh` / `clean-ingress-controller.sh`（ingress-nginx + 专用 ns `ingress-nginx`）
2. `elk`              → `deploy-elk.sh` / `clean-elk.sh`（logging/，ns `prd`）
3. `prometheus`       → `deploy-prometheus.sh` / `clean-prometheus.sh`（monitoring/，ns `prd`）
4. `ingress-svc`      → `deploy-ingress-svc.sh` / `clean-ingress-svc.sh`（console/ = Console Backend+Frontend+Ingress，ns `prd`）
5. `gateway`          → `deploy-gateway.sh` / `clean-gateway.sh`（本地 docker 网关 + port-forward 兜底）

### 调度器用法
- 全量部署（含重建镜像）：`bash deploy/deploy-all.sh`
- 全量但跳过 build：`bash deploy/deploy-all.sh --skip-build`
- 全量+先清理：`bash deploy/deploy-all.sh --clean` / `--skip-build --clean`
- 只重启/部署部分：`bash deploy/deploy-all.sh elk` / `bash deploy/deploy-all.sh ingress-controller prometheus`（可任意组合）
- 清理某套：`bash deploy/clean-all.sh elk` / `bash deploy/clean-all.sh ingress-svc`
- 全清理：`bash deploy/clean-all.sh --all`
- 帮助：`bash deploy/deploy-all.sh --help` / `bash deploy/clean-all.sh --help`
- 组件名白名单：`ingress-controller|elk|prometheus|ingress-svc|gateway`；未知参数 → 报错 exit 1。

### 关键设计约束（重要，下次别踩）
1. **共享 ns `prd`**：elk / prometheus / ingress-svc 三套都共用 `prd` 命名空间。
   - 全量 clean：删除顺序 `gateway → ingress-svc → prometheus → elk → ingress-controller`，最后删 `database`+`prd` ns + 强制清 Terminating finalizer + 清残留集群资源（ingressclass nginx、clusterrole/clusterrolebinding）。
   - **部分 clean 绝不可删 `prd` ns**：只 `kubectl delete -f <dir>/` 删该套资源，再删对应 clusterrole/binding；PVC 保留。
2. **"重启"语义（部分部署）**：组件脚本对 `kubectl get -f <dir> -o name` 过滤出 `deployment|statefulset|daemonset`，
   逐个 `kubectl rollout restart <kind>/<name>` + `kubectl rollout status`（不是重 apply 全量，避免影响 prd 内其他套）。
3. **gateway 特殊性**：它是本地 docker 容器 + `kubectl port-forward ... ingress-nginx 30000`，clean 时 `docker rm -f k8s-gateway` + kill port-forward pid；deploy 时 port-forward 兜底 + `/api/clusters/create` 用空 kubeconfig（in-cluster 配置）。
4. **MSYS 路径转换坑（实跑时踩到，已修）**：本环境 `MSYS_NO_PATHCONV=1` 且 `MSYS2_ARG_CONV_EXCL=*` 默认开启，导致 kubectl.exe/docker.exe 收到的 `/d/...` POSIX 路径不被转成 `D:\...` → 首次实跑 `kubectl apply -f /d/.../deploy/database/` 报 "the path ... does not exist"。修复：所有脚本顶部 `source deploy_one_by_one/_env.sh`，该文件 `unset` 两个变量（恢复正向转换）并兜底 `docker()` 函数转发 `docker.exe`。`gateway/start.sh` 的 `docker run` 自带 `MSYS_NO_PATHCONV=1` 内联前缀（它用 `pwd -W` 拿 Windows 路径、容器路径 `/etc/nginx/...` 不能被转换），与 _env.sh 不冲突，保持不变。

### 三个关键坑（实跑时踩到并已修，下次别再踩）
1. **`kubectl delete` 默认无限等待（clean-all 卡死）**
   kubectl 1.36 的 `delete` 默认 `--wait=true` 且 **timeout 无限**；若某 ns（如 ingress-nginx）残留 finalizer 卡在 `Terminating`，`kubectl delete -f <dir>` 会**永远挂起**。
   修复：所有 clean 的 `kubectl delete` 加 `--wait=false`；`_env.sh` 新增 `k8s_delete_ns()` 兜底——先 `--wait=false` 删 ns，再循环 45 次 patch 掉 finalizer 直到 ns 消失。
2. **`kubectl get -f <dir> -o name` 返回 `kind.group/name`，不写 ns 会 abort 部署**
   该命令输出形如 `statefulset.apps/elasticsearch`（带 `.apps` 组后缀）。原脚本拿它直接 `kubectl get "$r"`（无 `-n`）取 `.metadata.namespace` → 空 → 后续 rollout 命令失败 → `set -e` 在 ELK 步骤直接把整轮部署 abort（EXIT 1）。
   修复：在 `deploy-elk.sh`/`deploy-prometheus.sh`/`deploy-backend-app.sh` 的 rollout 循环里把组后缀剥掉（`res="${r%%.*}/${r##*/}"`）并**硬编码 `-n prd`**，rollout status 前加 `timeout 200` 兜底。`ingress-controller`/`database` 因为各自独立 ns，也统一走 timeout 包裹。
3. **网关 502 根因：host.docker.internal 的 IPv4/IPv6 错位 + port-forward 失效（--network host 终极修法）**
   最初网关用 `--add-host=host.docker.internal:host-gateway -p 9001:80` + `proxy_pass http://host.docker.internal:30000`。
   坑：容器内 `host.docker.internal` 同时解析到 IPv4(192.168.65.254) 和 IPv6(fdc4:f303:9324::254)，而 NodePort 的 port-forward 只监听 IPv4 → nginx 选了 IPv6 → 502；且前台部署一结束，后台 port-forward（PID）被回收，30000 端口更没人转发。
   终极修复：`deploy/gateway/start.sh` 改为 `--network host`（去掉 `-p` 与 `--add-host`）；`deploy/gateway/nginx.conf` 改为 `listen 9001; proxy_pass http://127.0.0.1:30000;`（host 网络下 127.0.0.1 即宿主机回环，直连 NodePort，无需 port-forward，也无 IPv6 错位）。重建网关后 Frontend/API 立即 200。
   - 备注：本机 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:9674` 会拦截 FQDN `k8s-cicd.daiyi.local.com:9001`（不在 NO_PROXY）。用 `localhost:9001` 或 `curl --noproxy '*'` 即可绕过 → 200，这是**宿主机侧代理**现象，不是集群问题。

### 调试经验（下次有用）
- **后台任务 harness 的假"completed"**：`run_in_background` 的任务偶尔在子进程（kubectl）还在跑时就回报 "completed"（孤儿进程往断管写）。不要信 TaskOutput 快照，以 `tasklist`/集群实际状态为准；最终验证放前台 + `tee` 落盘最可靠，`timeout` 包裹作防御。
